# Archway private TypeScript helper protocol v2

Protocol v2 contract; runtime adoption and acceptance are separate gates. Request/response schemas use JSON Schema Draft 2020-12. This integer protocol_version is independent of the public CLI JSON and YAML policy versions. Schemas are closed objects; incompatible additions require a private version change. Version 2 requires raw symlink witnesses on every input; version 1 is rejected, with no dual-version negotiation. Public JSON and policy versions remain 1. Node/TypeScript exact supported builds are fixed by the compatibility decision, not negotiated by input. The adapter launches the supplied helper entry point with the approved Node binary and bundled Compiler API, not a project-supplied executable.

## Lifecycle and framing

One process, one request, one response per declared TypeScript project. stdin is exactly one UTF-8 JSON object followed by EOF. stdout is exactly one UTF-8 JSON object followed by EOF; surrounding JSON whitespace is allowed. Reject malformed UTF-8, BOM, duplicate object keys at any depth, trailing non-whitespace, multiple JSON values, partial envelopes and unknown keys. stdout is reserved for the envelope. stderr is diagnostics, never evidence. No streaming, restart, automatic retry, dynamic plugin loading, project build, package installation, or lifecycle script execution. Compiler configuration is read as data; do not load project compiler plugins or user loaders. These execution choices are not an OS sandbox or a promise to contain hostile compiler/runtime bugs.

Adapter preflight: 5 seconds, 64 KiB captured output. Project request: at most 8 MiB; stdout response: at most 64 MiB; stderr: at most 256 KiB. MiB=1,048,576 bytes; KiB=1,024 bytes. Limits count raw bytes, not decoded characters; equality is accepted. Check request size before spawn. The 120-second monotonic project deadline runs from spawn through both process exit and stream EOF. First byte exceeding any cap invalidates the complete response. No silent truncation or partial acceptance. Termination/reap is best effort with an additional 2-second cleanup budget; unconfirmed cleanup adds a tool_error and prevents launching further helpers in this invocation. Do not promise process-tree termination or guaranteed cleanup on all operating systems.

A transport-successful helper exits 0, including an envelope whose analysis status is failed. Nonzero exit, signal, timeout, overflow, absent EOF or any schema/correlation/path failure invalidates the whole project envelope, including apparently usable partial facts. A syntactically and semantically valid failed envelope with exit 0 may retain verified facts. Invalid project envelopes do not discard previously validated evidence from other projects. Preflight/launch failure produces adapter-owned failure diagnostics without inventing a helper envelope.

## Request and membership

request_id is opaque and unique within one check; project_id is the exact policy project ID. The adapter derives public context_id as exactly 'typescript:' plus project_id; one explicit config means one context per TS project. Config paths and content hashes belong to the input identity, not context_id. The helper need not repeat this derivable field on every fact. root_uri is the canonical absolute file URI of the repository root, with no trailing slash except a filesystem root. config_path is the explicit tsconfig repository-relative path, never inferred from working directory. expected_files is the complete sorted TypeScript policy corpus, not just files already assigned to this project. The same corpus is supplied to each declared TS project so each can report membership in one pass. Discovery and analysis happen together; there is no second helper request or hidden retry. Construct each Program once per invocation and reuse it for membership and fact extraction. Internal read reuse is invocation-local only: preserve conflicting observations rather than overwriting them, and keep the parent's final independent revalidation. No persistent cache is introduced.

The helper constructs the configured Program, with the supported configuration/reference behavior fixed by the project-assignment matrix, and reports membership using its actual source files. It must not force corpus files into compiler rootNames to fabricate membership. Every expected file has exactly one row, in request order:

- member: this supported compiler context contains the file; coverage is complete, partial or failed.
- nonmember: membership was determined and the file is absent; coverage is not_applicable and input_id is null. This is not automatically a project error because another declared project may own it.
- unknown: configuration/Program failure prevented determining membership; coverage is failed and input_id is null. It requires incomplete or failed status plus diagnostics.

Inspection combines all project results and requires exactly one supported member context per corpus file. Zero, multiple, or unresolved candidate contexts produce incomplete and explicit candidates; no nearest-tsconfig/rootDir heuristic. It must not evaluate policy against a silently chosen ambiguous context. Helper status complete only describes this project's reliable membership/analysis, not overall corpus assignment.

## Paths, spans and facts

All repository paths are '/'-separated NFC, relative, case-sensitive, with no empty, '.' or '..' segments, backslash, drive prefix, NUL, or trailing '/'. Absolute physical identities use canonical file URIs, properly percent-encoded, without query, fragment, credentials or remote authority. Validate these properties and actual root correspondence in addition to schema patterns. Preserve disk spelling, reject aliases/collisions as the path matrix requires; never lowercase physical paths.

source and source_range.path must match an expected member source. Positions are 1-based line and UTF-16 column, end-exclusive; range must be nonempty, ordered, and within the exact decoded source bytes represented by its input hash. CRLF is a single line break; astral characters count two columns. A fact range covers the full import/export/require/import-type expression or declaration being reported, not a fabricated target span. specifier is the decoded literal module string. type_only records a type-only dependency; it does not promise runtime loading.

Kinds: import (including import-equals), export (including re-export), import_type, require and dynamic_import. Only statically supported literal references produce resolved facts. Computed import strings produce unknowns with positions. Syntax/unsupported constructs make coverage partial with unknowns; retain independently verified facts. A nonliteral expression is not represented with an invented specifier.

The complete-coverage promise is limited to supported explicit module-reference syntax. A recognized explicit dependency reference that the five fact kinds cannot represent must produce a positioned unknown and partial coverage, not a fabricated kind or a quietly complete file. This includes explicit TypeScript triple-slash path/types references and external-module augmentation references until supported by a deliberate protocol extension. Resolve language context before identifying an augmentation: an ambient module declaration in a global script declares a module rather than itself referencing a file. Global declarations, ordinary SDK globals, and implicit symbol coupling are outside this explicit-reference guarantee; their mere presence does not cause blanket incomplete coverage. An actual import of an ambient virtual module still needs proven target/classification evidence or an unknown under the normal rules. Verified independent facts remain usable when unsupported references make coverage partial.

resolution is exactly one variant:
- local: path is canonical repository-relative target, or null when physical local code lies outside the repository; canonical_file_uri always identifies its canonical physical target. via_path is the absolute observed alias URI when different, otherwise null. Inspection applies ownership/scope/exclude/root rules; helper never emits allowed/denied or policy violations. Workspace package code is local even when resolved through a package-manager alias. Targets follow the actual Program declaration/reference redirect, not merely an unredirected low-level lookup. The target is the directly referenced module file after those file/reference redirects, never the ultimate declaration file of an imported or exported symbol. Symbol-alias chasing is not file redirection: importing from a public barrel retains the barrel as the direct target even when its exported symbols originate in private implementation files. A prepared declaration output such as dist/index.d.ts remains the target when the actual Program redirects there; public designation of src/index.ts does not cover it.
- external: identity is the compiler/package-proven third-party package identity.
- builtin: identity is the compiler-proven SDK/builtin module identity.
- unresolved: no target was established; an unknown diagnostic is mandatory and status cannot be complete.

Every supported import/re-export occurrence is a separate direct edge. A barrel may re-export a same-owner private file; a cross-owner re-export must itself meet the directed allows and exact public-target predicates in Inspection. Do not synthesize consumer-to-origin edges through a re-export chain or infer transitive allows. Local exports without a module reference add no new direct edge, while any supporting imports remain checked. Entrypoint policy does not inspect symbol visibility or exported API provenance.

external/builtin require positive provenance, never just bare-specifier syntax. Classify origin before location: positively proven installed third-party code is external whether physically inside or outside root; repository/project/workspace/path-dependency code is local even outside root. Neither node_modules spelling nor a compiler external-library flag alone proves third-party origin. Conversely, broad owns prefixes and Program membership alone do not reclassify a proven installed third-party package as local. Conflicting or insufficient origin evidence produces unknown/incomplete rather than an assumed category. This target classification does not change the authoritative source corpus. Local outside-root evidence is retained for Inspection to report the boundary result. Target files need not belong to expected_files: the policy corpus governs sources, not all discovered dependencies.

## Provenance and revalidation

inputs records every filesystem observation that influenced configuration, membership, extraction and resolution, including tsconfig extends/references, package manifests/lock or resolution inputs actually read, source/declaration files, SDK libraries, directory enumeration and negative existence probes. Each observation has a unique opaque id, kind, observed_uri, canonical_uri and required symlink_hops; file/directory additionally have lowercase SHA-256. Existing paths require a canonical URI; absent observations use null. A repeated observed path with conflicting identities indicates changing input, not a choice to overwrite an earlier observation.

For files the hash covers exact bytes read. For a directory the hash covers UTF-8 compact JSON of its immediate entry records [name,type], sorted by Unicode codepoint name then type, where type is file, directory, symlink or other; no whitespace/BOM. Record separate observations when child existence/content/alias resolution affects the answer. Symlink provenance preserves the observed URI, canonical target and ordered raw-hop witness below; revalidation checks the full route as well as bytes. Negative probes record absence and every traversed hop before the missing component. Do not include unrelated files merely to inflate provenance.

Each input, including directory and absent observations, carries `symlink_hops`: an ordered array of closed `{observed_uri, target}` objects, or `[]` when no links were traversed. A hop URI names the encountered physical link entry after resolving preceding ancestors: normalized absolute file URI, no remote authority/query/fragment, filesystem-root URI or trailing slash. `target` is nonempty, NUL-free Unicode scalar text decoded strictly from the original readlink UTF-8 bytes, without NFC or path normalization. Relative/absolute targets, dot segments, root target text and a genuine U+FFFD are valid; replacement decoding and lone surrogates are not. No redundant target hash is added; ordinary file-byte and directory-inventory hashes remain unchanged.

Traversal records physical expansion order, including repeated completed hops. Repeating a URI is not itself a cycle: detect active expansion cycles and stop after at most 40 expansions per route. Cycles, unsupported link types, invalid UTF-8 or overflow make analysis incomplete; never present a truncated witness as complete evidence. JavaScript reads a Buffer and strictly decodes it. Dart validates raw native readlink bytes before any unsafe text readlink or realpath call; a byte-decoding failure must not terminate the CLI. Native buffer truncation must be detected, not accepted as target text. Platform support remains subject to the existing acceptance cells.

Structurally malformed witness shape/URI/text invalidates the response. A structurally valid baseline is accepted for independent retracing, even if its hops are now missing, extra, reordered or retargeted: disagreement yields `INPUT_CHANGED`/incomplete under the existing final-freshness retention rules, not a fabricated-envelope diagnosis. Public `changed_inputs` uses the affected original input location already represented in public identity; raw hop text stays private and no public schema field is added.

Track witness conflicts by observed route and physical link URI, separately from canonical content identity. Different stable alias routes may share a canonical file/hash. Different raw targets for the same physical link, including within one response claiming complete, are handled by the parent's observation-conflict reconciliation rather than rejected as structural errors. Parent aggregation must mark incomplete and invalidate affected project facts/discovery under the existing conflict rule, while preserving unaffected projects and independently established policy/corpus violations. Do not retain facts made unreliable by that conflict merely because a pure final freshness mismatch can retain baseline facts.

Every nonfailed member file row references its source file input. Every fact inherits the entire project input manifest, including shared configuration, membership and resolution probes. Its input_ids lists only direct source/target/classification evidence; do not duplicate the full shared configuration or negative-probe list on every edge. IDs must resolve, and fact source hash must match the file row. For local facts, at least one file input identifies the canonical target. For external/builtin, provenance must substantiate the classification. Facts from failed/nonmember/unknown file rows are forbidden. Files with no dependencies still need complete coverage and source evidence.

Inspection validates envelope against request, canonical paths, spans and input references, then independently revalidates the recorded observations and its own authoritative corpus inventory before finalizing check. Changes in bytes, mappings, absence probes or inventory mark incomplete. Known facts may be retained with their original input identity and change diagnostics; they must not be portrayed as a current atomic snapshot. This is detection of observed changes, not filesystem locking, an atomic snapshot, or proof against change-and-revert races. If the helper cannot supply trustworthy evidence, report partial/failed coverage rather than pretending a complete trace exists.

## Status and trust rules

complete: every expected row is complete member or determined nonmember, no unknowns/tool_errors, and no unresolved facts. incomplete: at least one unknown/tool_error explaining missing knowledge; verified facts may remain. failed: at least one tool_error explains project failure; verified facts may remain in partial/complete member rows. Empty facts do not prove no dependencies unless coverage is complete.

Diagnostics contain code, human-readable message, nullable path and nullable source_range. Present diagnostic range must match path; a zero-width diagnostic range is allowed (for example a parser insertion point), while edge ranges remain nonempty. Null represents a project-level issue or inability to locate bytes. Codes/messages are facts about extraction/configuration/transport, never architectural policy decisions. Adapter diagnostics for invalid envelope are generated locally; untrusted text is not promoted to facts.

Schema validation is necessary but insufficient. Semantic obligations include exact request/project correlation, unique sorted corpus coverage, member/coverage consistency, complete-status invariants, URI normalization/root mapping, source-span bounds, target identity, provenance references/completeness and observed input revalidation. The contract-test validator covers a finite subset and does not claim to implement filesystem validation or compiler behavior.

## Validation artifacts

request.schema.json and response.schema.json are normative structural schemas; protocol.md defines framing and semantic checks. fixtures/ contains the valid-request.json and valid-response.json seeds. The Dart helper contract tests derive valid and invalid cases in memory without writing fixture copies. From the repository root, prepare dependencies with `dart pub get`, then run `dart test test/contracts/helper_contract_test.dart test/contracts/helper_protocol_v2_test.dart test/contracts/helper_transport_test.dart`. These are contract tests only: they do not implement the package, launch a helper, prove supported runtime versions, execute compiler fixtures, exercise OS process cleanup, or validate actual compiler input tracing.

Required real regressions (not established by finite schema tests): an intermediate link changes while final file/hash stays fixed; a nonlink becomes a link to the same file; an absent child has a changed directory-link ancestor; omitted/reordered/extra witnesses differ on retrace; a source-boundary violation survives unrelated freshness change; invalid native UTF-8 reports incomplete without crashing; active cycles, more than 40 expansions and truncated native buffers never produce complete evidence.

## Loaded compiler verification

Before constructing a Program, compare actual loaded ts.version with the bundled release constant (5.9.3 for this release). A mismatch returns a schema-valid failed response with diagnostics in tool_errors and no usable compiler facts. It does not add a handshake or response field. The parent leaves public tool_versions.typescript null when this self-check failed; the bundled expected version is not evidence of the actual loaded compiler version. The same rule applies when the compiler cannot be loaded.

Parent aggregation follows json/decision.md's cross-project observation-conflict rule. A conflicting shared input invalidates facts and discovery from every dependent project's inherited manifest, including the baseline supplier, while preserving unaffected project evidence and independently established violations under incomplete.
