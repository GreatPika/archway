# Package delivery contract

The delivery formats are native archives, an npm package and a pub CLI package.
Delivery does not change the policy, public JSON or helper protocol versions.
This contract defines installation requirements and acceptance criteria; it does
not certify an implementation or delivery route.

## One core, three delivery forms

- The same Dart CLI core owns argument parsing, policy behavior, JSON, streams
  and exit codes. There is no second TypeScript implementation or public Dart API.
- Keep the three native AOT archives and original target cells from
  [decisions.md](decisions.md). Ship the required native bridge, helper, pinned
  TypeScript and lib files, schemas, version/hash manifests, licenses and guide.
- One npm package contains all three target AOT executables/native bridges and
  one shared asset tree. Its thin JavaScript `bin` launcher selects a fixed
  OS/CPU mapping and directly spawns the payload with unchanged argv and streams;
  the core decides CLI usage and results. Preserve core exit codes and test
  termination/signal behavior on each OS without promising identical signal
  semantics. Pre-launch errors are distinct from the core JSON contract.
  Unsupported targets fail explicitly.
  No shell invocation, optional platform packages, lifecycle/install scripts,
  downloads or builds are part of this package's installation or launch; npm
  users need no C compiler.
- The pub CLI package contains Dart source for the same core, prebuilt native
  bridges and the same generated helper/compiler assets. The supported command
  is `dart pub global activate archway`, then the explicit installation step
  `dart pub global run archway:setup`, followed by `archway` with the pub bin
  directory on PATH. Repeat setup after every activation or update. On the pinned
  SDK, setup repairs only the verified Archway launcher generated by pub: POSIX
  snapshot quoting and Windows fallback exit-status propagation. Ordinary commands
  never mutate launchers. Recognized path-activation launchers need no repair.
  Stock activation alone remains affected by these launcher defects; it is not the complete supported installation sequence. Dependency-local `dart run archway:archway` is advertised
  only after its own installation test passes. No `dart install` flow is promised.
- npm users need Node to launch, but no Dart SDK for policy commands or TypeScript
  check. Pub users need Dart to launch. Policy/query/init/export require no
  additional analysis runtime; the native payload itself requires neither Node
  nor an external Dart SDK. TypeScript check still needs verified external Node;
  Dart check still needs the verified external SDK. Exact runtime/compiler pins
  in decisions.md are unchanged. Node and the full SDK are not bundled or
  downloaded implicitly.

## Private installation layout

One small private layout owner locates Archway's own package URI for Dart source
execution, or the canonical native executable at `bin/<target>/archway` (Windows:
`archway.exe`). Native bridges are fixed under `native/<target>/`; shared assets
are under `assets/`. Moving the entire staged installation is supported. Moving
only a payload or losing required assets fails the affected operation explicitly.
Single-target archives use the same fixed layout, and direct native invocation
is supported. Stage build/test outputs into this layout rather than guessing
arbitrary executable ancestors. This is an internal dependency shared by
consumers, not a new public module seam.

Source development and both package channels use the generated
`assets/typescript/vendor/typescript/` tree, containing the unmodified pinned npm TypeScript package, including its lib files
and license. Build-time preparation uses the pinned lock; runtime resolves only
this fixed compiler path and the fixed helper path. There is no fallback to
`node_modules`, cwd, project compiler, ad hoc upward package-config search or
network. Package contents must include these assets after npm packing and pub's
packaging filters.

The explicitly invoked Archway installation is trusted even when installed inside
the inspected root, including a local devDependency. Anchor that installation
independently of the inspected project's configuration; retain canonical/no-alias
checks for its payloads, helpers, compiler and native bridges. Do not reject the
whole installation merely for being inside root. This trust does not authorize
project wrappers, plugins, loaders or arbitrary runtime executables. External
runtime discovery and environment/loader filtering remain as in decisions.md.
The launcher/runtime boundary is not a sandbox against a modified installation
or influence applied before the launcher starts. Manifest hashes support build
provenance and acceptance, not runtime signature or authenticity guarantees.

Installation location never silently changes scope minus exclude. If the user
selects installed sources/assets, they remain in the authoritative corpus under
the normal coverage rules; guides should explain explicit scope/exclude choices.

## Required installation evidence

On every original target cell, verify actual packed npm local `-D`, global and
cache/exec invocation with scripts disabled, then run offline from another cwd,
including spaces/Unicode, decoy project assets and an in-root installation.
Prove the cache route actually selected cached package bytes rather than a local
`npx` candidate; inspect packed file inclusion and measure final package size.
Exercise native relocation, policy/init/export without Dart, TypeScript check with pinned Node and without
Dart, missing/wrong Node, unsupported target and missing/corrupt/no-alias assets.
Compare core arguments, JSON, streams and exits; launch failures must be explicit,
never a successful architecture result. Include an explicitly selected installation
in corpus coverage and a fixture with user-declared exclusion.

For pub, inspect the publishable file set with a publish dry-run and activate
exactly that staged content in an isolated cache with prepared dependencies; run
the resulting `archway` after explicit setup from another cwd and exercise native
writes and the shared assets. Include spaces/Unicode in PUB_CACHE, exact-template
refusal controls, setup idempotence and reactivation followed by setup. Prove
snapshot execution by poisoning the still-present installed entrypoint and showing
that direct source fails while the installed command succeeds.
Include missing Node for TypeScript and policy commands with no Node. If tested,
record dependency-local execution separately. Staged/path activation and packed
content inspection are not hosted-registry installation verification. Archive,
npm and pub evidence must identify artifact bytes, versions, platform and route.
Release requires measured evidence for every gate. This contract does not
authorize public registry publication, credential use or release.

## Registry-ready staging boundary

Ordinary source checkouts and default developer package stages remain private.
Maintainers may explicitly request `--registry-ready` for complete all-target npm
or pub staging. This sets final publication metadata before the package inventory
is hashed; it never publishes, authenticates, reserves a name or certifies a route.
Partial Linux-only stages cannot opt in. Source `pubspec.yaml` remains private;
the staged pubspec changes only its publication destination to `https://pub.dev`.
Package versions, runtime pins and dependency constraints remain unchanged.

Registry-ready metadata is preparation only. Full package validation, archive-byte
identity, installed-route evidence and separate publication authorization remain
required. A candidate must not be made publishable by editing certified bytes.
