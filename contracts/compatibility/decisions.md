# Archway v1: pinned compatibility matrix and paths

Normative v1 matrix.

## 1. One version per component

- Dart SDK for analysis and CLI compilation: **3.13.3 stable**. Embedded `analyzer`: **14.5.0**, exact dependency and lockfile, no `^` in the release manifest.
- Node for the shipped helper: **24.21.0 LTS**. Shipped TypeScript JavaScript Compiler API: **5.9.3**, exact dependency and lockfile. The project's TypeScript is not loaded; its presence or different version does not affect analysis. The report explicitly identifies bundled 5.9.3. Compatibility is not promised for projects requiring different semantics/options.
- Compatibility is limited to these exact versions. Any other runtime version makes only the affected project incomplete. Add a patch version by changing the release manifest and rerunning the matrix; no automatic latest/update. Check security patches before release; do not publish a known-vulnerable pin merely to match the number.
- Experimental Dart language flags, custom SDKs, Bazel/GN, Yarn PnP, custom loaders/resolver plugins, and TS native preview are unsupported in v1. Ordinary Dart and TypeScript packages in one repository are supported. Flutter projects are within the target envelope only with a stable SDK containing Dart **3.13.3**, readable SDK libraries/summary, package_config formatVersion=2 after the user has already run pub get, and resolvable Flutter package mappings. Record Flutter version/revision and SDK manifest hash in evidence; do not run Flutter CLI. Incomplete cache/missing generated source yields incomplete. This is a compatibility predicate, not a claim that a Flutter release has been tested; a required Flutter fixture for every target archive checks flutter package import, dart:ui, parts, generated imports, and missing SDK cache. The [official archive](https://docs.flutter.dev/install/archive) publishes Flutter/Dart mappings.
- Dart languageVersion: stable null-safe versions from 2.12 through 3.13 inclusive; per-file override must not exceed the package language version. Newer, legacy, and experimental variants yield incomplete rather than a retroactive version change. package_config formatVersion=2; configuration is already prepared by the user. No pub get/install, generation, or analyzer plugin execution during check.

Sources confirm version existence and upstream properties, not Archway integration: [Dart 3.13.3, released 2026-09-01](https://raw.githubusercontent.com/dart-lang/sdk/3.13.3/CHANGELOG.md), [analyzer 14.5.0](https://pub.dev/packages/analyzer/versions/14.5.0), [analyzer minimum SDK 3.11](https://pub.dev/packages/analyzer/versions), [Node 24.21.0 LTS, released 2026-09-08](https://nodejs.org/en/blog/release/v24.21.0), [TS 5.9.3](https://github.com/microsoft/TypeScript/releases/tag/v5.9.3).

## 2. Corpus and configurations

Normative details of single-context assignment are in the neighboring project assignment contract. Corpus: `.dart`, `.ts`, `.tsx`, `.mts`, `.cts`, including `.d.ts`, `.d.mts`, `.d.cts`; extension matching is case-sensitive. `.js/.jsx/.mjs/.cjs`, Vue/Svelte, and virtual sources are not a supported language corpus. An unsupported local imported target must not be disguised as external: it yields incomplete while preserving any known ownership violation.

TS `allowJs:true` and `noResolve:true` are unsupported: complete checking cannot be promised with an undefined JS corpus model or disabled resolution. TS project references are supported only with prepared disk outputs under the standard TS5.9.3 CompilerHost, without a source-redirect hook, building, or automatic discovery of YAML projects. A missing referenced config/output yields incomplete; `.d.ts` output is an ordinary local target, not silently replaced with source. Leaf tsconfig files in a monorepo may be listed as separate projects; a file in multiple contexts remains ambiguous rather than being chosen by order. Includes outside the tsconfig directory but inside root are allowed; rootDir does not define membership. Standard valid target/module/moduleResolution combinations in pinned TS5.9.3 are supported as validated by Compiler API, except for the explicitly listed semantic exclusions. Required representative fixtures: Node16/Node16, NodeNext/NodeNext, Preserve/Bundler, ESNext/Bundler, CommonJS/Node10; targets ES2020/ES2022/ESNext. These are test representatives, not a target whitelist. JSON/JSONC extends through Compiler API locally or from an installed package, paths/baseUrl, and ordinary npm/pnpm workspace aliases are supported. The assignment contract defines detailed effective parameters; this table does not expand them. Selected scope files with recognized unsupported code extensions `.js/.jsx/.mjs/.cjs/.vue/.svelte` yield incomplete, not a silent zero corpus.

## 3. Delivery: finite target list

Three target archives: `linux-x64` for Ubuntu 24.04 LTS/glibc; `macos-arm64` for macOS 15/APFS; `windows-x64` for Windows 11 24H2/NTFS. These are deliberately three platform cells for testing POSIX and Windows, not a promise covering all distributions/OS versions. ARM Linux, Intel macOS, Windows ARM, musl/Alpine, network filesystems, and emulation are outside the v1 support envelope.

The archive contains a native AOT CLI, native bridge, helper JS, a closed set of TypeScript 5.9.3 and its lib files, a version/hash manifest, licenses, and a guide. The 0.2.0 preview delivery adds thin npm and pub launchers that acquire the pinned native archive for the selected target on first invocation; [delivery.md](delivery.md) defines the exact layout and acceptance. Node and the full Dart SDK are not bundled. Native Plan/query/init/export work without either external runtime; the npm launcher requires Node and the pub snapshot launcher requires pinned Dart for activation and explicit global-run invocation. These commands do not start additional analysis runtimes. Dart check requires the SDK; TS check requires Node. Resolve assets from the installation's own package URI or canonical staged executable, not cwd or the checked project. Moving the whole installation is allowed; missing required assets cause an explicit error for the affected operation. No brew installer, lifecycle/install scripts or native-payload/analysis-compiler builds at startup. Only the thin wrapper may acquire its pinned native payload before invoking the core; inspection never downloads dependencies or runtimes. Offline warm invocation is required with verified native bytes and, for pub, a prepared activated snapshot under the same SDK; SDK-switch and missing/stale-snapshot behavior require separate measured acceptance.

A cell moves from `target, not tested` to `certified` only after building and unpacking the archive in a clean VM of that OS/architecture, running all contract fixtures from a different cwd, testing paths with spaces/Unicode, SDK/Node absence and failure cases, and verifying offline operation/no project-code execution. v1 readiness requires all three cells and the package-route gates in delivery.md; otherwise explicitly revise scope before release rather than silently marking it supported. This does not authorize package publication. [Dart native executables](https://dart.dev/tools/dart-compile) and [SDK archives](https://dart.dev/get-dart/archive) explain the delivery mechanism; they do not replace testing these targets.

## 4. Lexical paths: identical on every OS

1. `--root` is separate: an existing directory accepting native absolute/relative form. Canonicalize it once to the physical root. A symlink for root itself is allowed as an explicitly chosen root; this does not authorize child symlinks.
2. YAML `scope/exclude/owns` paths, relative configurations, and positional owner/allows paths are always repository-relative. `/` and `\\` are separators on every OS; the result uses only `/`. A POSIX filename containing a literal backslash is unrepresentable and yields incomplete when discovered.
3. Before normalization, reject absolute/UNC/device/drive-relative (`C:foo`) forms, URL schemes, NUL/control characters U+0000–001F/U+007F, `:*?"<>|[]{}`, Windows device segments CON/PRN/AUX/NUL/COM1–9/LPT1–9 (also with extensions, case-insensitively), and components ending in a space or dot except special `.` and `..`. Brackets `[]` and `{}` are also forbidden in all v1 policy and positional paths; discovering such a name in the corpus yields incomplete as an unrepresentable portable path. This is one portable subset; `%2e%2e` is not URL-decoded.
4. Normalize Unicode to NFC; preserve case. Empty paths are forbidden. Remove empty interior segments and `.`; `..` pops the preceding segment. An attempt to pop an empty stack is immediately forbidden even if later segments would return under root. `a/../b` => `b`; `../root/b` is invalid. Root as a directory prefix is `./`; `.` and `a/..` also normalize to `./`.
5. An original trailing separator preserves directory-prefix meaning. Otherwise the path is an exact file, except for normalized root. `src` and `src/` differ. Match prefixes at segment boundaries; `src/` does not include `src2/x.ts`. `A` and `a` differ even in a Windows policy-only query. No stat/realpath for future paths.
6. Normalize the whole policy first, then check owns overlaps. Merge duplicate/nested paths of one owner; overlaps between different owners are forbidden regardless of file existence. `exclude` takes precedence over scope/owner. YAML-path error => invalid policy/exit2; invalid positional CLI-path => usage/exit64.

These are Archway semantics, not a claim that every host filesystem is case-sensitive. [Windows naming](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file) explains why OS path APIs alone cannot define policy identity.

## 5. Physical verification: check

- Corpus traversal uses lstat on each segment; included file symlinks, directory symlinks, and junction/reparse aliases are not traversed and yield incomplete with the original lexical path. The corpus behind them is not considered successfully empty. An explicitly excluded subtree is not traversed; an import into it is still checked as a local target and a violation if confirmed.
- The physical canonical target after resolution is required in addition to the lexical path. Check containment by canonical-root segments, not a string prefix. Identical actual content does not change the policy owner.
- Every segment of an ordinary included file must have exactly the spelling seen in directory entries after NFC. Case mismatch on a case-insensitive filesystem yields incomplete; ownership of future `src/A.ts` does not arbitrarily become ownership of `src/a.ts`. Two names collapsing after NFC or resolver canonical pathname yield alias ambiguity unless there is one compatible identity/owner. Two actual files differing in case on Linux remain distinct.
- Physical identity in v1 means the canonical pathname observed through resolver/realpath, not inode or byte equality. Two hardlink directory entries remain distinct paths and owners; check imports to each path by the actual resolved name. Detectable canonical/resolver aliases with ownership conflicts yield incomplete. Discovering all hardlinks or treating inode equality as policy identity is outside this contract. An inaccessible/unknown reparse type still prevents confirming safe traversal.
- The only symlink exception is a resolver package-manager alias that is not an included corpus source. An npm/pnpm node_modules alias may resolve to an ordinary physical file; retain original specifier, logical resolved path, symlink hops, and canonical target. Classify provenance before checking location: compiler/package manifest + lock/config evidence must distinguish an installed third-party package from a repository/project/workspace/path dependency. Presence under canonical root, a node_modules segment, bare specifier, or compiler external-library flag alone does not prove the category. Broad owns ["./"] and membership in Program.getSourceFiles() also do not reclassify a proven installed third-party package as local. An alias does not add a second owner. A source behind a symlink in scope remains forbidden even if the alias looks like a package path.
- A confirmed installed third-party package is external whether its canonical target is inside root (ordinary node_modules or an internal pnpm store) or outside. A confirmed repository/project/workspace/path dependency remains local regardless of location: inside root, owner follows the canonical repository-relative target; outside, known local outside_scope => violation. Ambiguous or contradictory provenance yields incomplete, not external by default. An SDK source is builtin only from a verified SDK root. Changes in owner/status between physical aliases => incomplete; retain already reliable violations. This target classification does not reduce the authoritative source corpus of scope minus exclude: explicitly selected vendor/source files do not automatically disappear.
- Cyclic/unreadable symlinks, escapes, file/config/alias-chain changes during reading, and unconfirmable canonical identity yield incomplete. The list and hashes of read inputs, including configurations, package manifests/lockfiles, and alias evidence, form part of input identity. This detects changes within the check window; it does not promise a filesystem snapshot or protection against a malicious concurrent writer.

## 6. Runtime preflight and helper boundaries

CLI uses direct spawn with argv, without a shell. Look up an external runtime through PATH once and pin its absolute executable; reject cwd/empty PATH entries and repo-local executable substitutions. An explicitly invoked Archway installation may reside inside the repository under delivery.md; this does not authorize repo-local external runtimes. Do not execute repository wrappers, npm scripts, hooks, or project plugins. Clear NODE_OPTIONS, NODE_PATH, and loader/preload influence before version checking and helper execution. Analyze user code as data.

Version preflight: 5 seconds wall time, up to 64 KiB output. Also verify Dart SDK through readable version metadata and SDK libraries; do not replace embedded analyzer with the project's analyzer. Node preflight runs only a version query; the helper confirms its protocol/compiler version. Missing/different runtime/corrupt assets => affected project incomplete; continue analysis of the other language. No fallback to another version, downloads, or automatic installation.

Per TS project: 120 monotonic seconds from spawn to exit+EOF; request ≤8 MiB UTF-8, stdout response ≤64 MiB UTF-8, stderr ≤256 KiB. Exactly the limit is allowed; the first excess byte is an error. After timeout/limit/cancel, terminate and reap with up to 2 seconds for cleanup; if the process is not confirmed stopped, report an explicit tool error and do not launch further helpers. Do not silently truncate evidence or accept JSON before stream closure/successful exit. One request/response; no retry/streaming. Discard an invalid project response entirely, retaining verified facts from other projects and independent policy/corpus violations. These numbers are product resource budgets, not measured performance. Version budget changes with the release manifest.

## Implementation acceptance

Release acceptance requires real fixtures on all three target OS/architecture combinations and confirmation that incomplete analysis cannot report success and that inspection performs neither network access nor project-code execution. `adversarial-cases.json` defines expected-behavior scenarios; `test_lexical_reference.py` tests a finite lexical model, not the host filesystem.

Compiler self-check: before creating Program, the helper compares the actually loaded ts.version with the shipped constant 5.9.3. A mismatch returns a valid failed response with a diagnostic in tool_errors and no usable compiler facts. The private schema is unchanged; public tool_versions.typescript remains null if the actual version failed verification. The manifest version alone does not confirm the loaded compiler.

## Compiler host feasibility gate

Before expanding the CLI, verify on small real projects with pinned versions: positive reads, negative probes and directory inventories, prepared TypeScript redirects, every Dart conditional URI branch, and analyzer context assignment. Verify that evidence reaches input_identity and the final independent reconciliation. If reliable tracing is impossible, stop implementation expansion and clarify the supported boundary; a fixture model does not replace this gate.

The exact bounded installed-provenance classifier is in package-provenance.md. Supported joins: npm lockfileVersion 2/3, pnpm lockfileVersion 9.0, pub package_config v2 with selected lock/workspace/SDK metadata. Other formats do not default to external.
